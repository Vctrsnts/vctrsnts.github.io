Mejorando mis containers con healthchecks

2026-11-15 · 7 min · @Self-Hosting · #Podman #Dockge #VPS

Aquí tenemos otro artículo nuevo, aunque no lo considero como un artículo más, sino como un añadido que podría incluirse en este o en este otro, porque son mejoras o información adicional que siempre viene bien tener disponible cuando trabajamos con nuestros contenedores.

◇ Añadiendo healthchecks a los contenedores

Antes de ponerme con la configuración de las notificaciones de Beszel, de la que ya hablaré en otro artículo, quería dar un paso más en la supervisión de los servicios que tengo funcionando en mi VPS.

Una cosa es que un contenedor esté en ejecución y otra muy distinta es que el servicio que contiene esté funcionando correctamente. Un contenedor puede aparecer como iniciado (running), pero, si la aplicación que ejecuta tiene algún problema, nosotros seguiremos viendo que el contenedor está en marcha.

Para solucionar esto existen los healthchecks, que son comprobaciones periódicas que permiten verificar si un servicio responde correctamente y asignarle un estado de salud.

Lo mejor de todo es que Podman permite definir estas comprobaciones directamente en el archivo compose, sin necesidad de instalar herramientas adicionales de supervisión.

En mi caso, quería añadirlas a cinco servicios: Memos, Element, Continuwuity, Nginx y FlexGet.

Para hacer estas comprobaciones podemos utilizar dos aplicaciones:

  • wget
  • curl

No son obligatorias, pero son las más aconsejables. Y, si ya tienes alguna de ellas instalada, no hace falta añadir nada más.

◇ Memos

Empecé por Memos, que fue uno de los casos más sencillos.

La imagen de Memos ya incluye wget, así que lo utilizaremos para comprobar que el servicio web responde correctamente.

Pero, antes de empezar a modificar el compose, lo primero que hice fue realizar una prueba desde el propio contenedor para verificar que funcionaría correctamente:

user@ares ~> podman exec memos wget -q -O /dev/null http://127.0.0.1:5230/

Si el comando devuelve un código de salida 0, significa que la petición se ha realizado correctamente.

Una vez comprobado que todo funcionaba, solamente faltaba añadir el siguiente bloque al servicio memos:

    healthcheck:
      test: ["CMD", "wget", "-q", "-O", "/dev/null", "http://127.0.0.1:5230/"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 40s

Nota

Este bloque lo voy a utilizar en más servicios, porque es el que recomienda la documentación de Podman.

Con esta configuración, Podman comprueba cada 30 segundos que Memos responde a través de su servidor HTTP. Si falla tres veces consecutivas, el contenedor pasará al estado unhealthy.

◇ Element

El siguiente fue Element, que comparte el archivo compose con Continuwuity.

En este caso, la imagen también incluye wget, así que podemos utilizar el mismo procedimiento. Lo único que cambia es el puerto: Element sirve su contenido a través del puerto 80.

Primero comprobé que respondía correctamente:

user@ares ~> podman exec element wget -q -O /dev/null http://127.0.0.1:80/

Una vez confirmado que la petición funcionaba, añadí el healthcheck:

    healthcheck:
      test: ["CMD", "wget", "-q", "-O", "/dev/null", "http://127.0.0.1:80/"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 40s

Hasta aquí todo había sido bastante sencillo. Pero el siguiente servicio iba a ser un poco diferente.

◇ Continuwuity

Aquí me encontré con el primer inconveniente.

La imagen oficial de Continuwuity es extremadamente minimalista. Está construida a partir de scratch y no incluye herramientas habituales como wget, curl o incluso una shell.

Por tanto, aunque el servidor dispone de una API HTTP que podemos consultar, no tenemos ninguna herramienta dentro del contenedor para realizar esa petición.

Así que decidí utilizar el endpoint que tenemos disponible:

/_matrix/client/versions

Esta es una dirección de la API de Matrix que devuelve información sobre las versiones compatibles del servidor.

La solución que encontré fue aprovechar BusyBox, que ya tenía instalado en el VPS. BusyBox incluye una versión reducida de wget y permite realizar la comprobación sin modificar la imagen original de Continuwuity.

Primero comprobé que BusyBox estaba disponible:

user@ares ~> /usr/bin/busybox wget --help

Después añadí un volumen al servicio continuwuity para que el contenedor pudiera utilizar ese ejecutable. Lo importante es que el montaje sea de solo lectura (:ro):

    volumes:
      - ${PODMAN_STORAGE_PATH}/matrix:/var/lib/continuwuity
      - /usr/bin/busybox:/usr/local/bin/busybox:ro

Una vez recreado el contenedor, podemos verificar que ya es posible utilizar BusyBox desde dentro del propio contenedor:

user@ares ~> podman exec continuwuity /usr/local/bin/busybox wget -q -O /dev/null http://127.0.0.1:8008/_matrix/client/versions

La prueba devolvió un código 0, así que ya tenía todo lo necesario para configurar el healthcheck:

    healthcheck:
      test:
        - CMD
        - /usr/local/bin/busybox
        - wget
        - -q
        - -O
        - /dev/null
        - http://127.0.0.1:8008/_matrix/client/versions
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 40s

De esta manera, seguimos utilizando la imagen original de Continuwuity. Simplemente le proporcionamos un ejecutable externo mediante un volumen de solo lectura.

Nota

Es importante que el montaje sea únicamente de lectura (ro). De esta manera, si se produjera algún acceso no deseado a ese contenedor, no podría modificar el ejecutable original del host.

◇ Nginx

El siguiente servicio fue Nginx, que utilizo para servir los archivos relacionados con los podcasts que sigo.

En este caso, la imagen nginx:stable-alpine ya incluye wget, así que no necesitamos montar ninguna herramienta adicional.

Sin embargo, al realizar la primera prueba me encontré con un pequeño problema:

user@ares ~> podman exec nginx /usr/local/bin/busybox wget: server returned error: HTTP/1.1 403 Forbidden

No era un problema de Nginx. Mi configuración está preparada para permitir el acceso a determinados archivos, como imágenes y feeds RSS, mientras que el resto de las direcciones están bloqueadas.

Por tanto, consultar la raíz del servidor (/) no era una buena opción para el healthcheck.

Decidí crear una ruta específica para estas comprobaciones: /healthz.

Dentro del bloque server de mi nginx.conf, añadí lo siguiente:

        # Healthcheck interno
        location = /healthz {
            allow 127.0.0.1;
            deny all;

            access_log off;
            auth_basic off;

            return 200 "OK";
        }

Esta ruta devuelve una respuesta HTTP 200 y evita que tengamos que utilizar uno de los archivos protegidos para comprobar el funcionamiento de Nginx.

Después de reiniciar el contenedor, comprobé que funcionaba:

user@ares ~> podman exec nginxPodcast wget -q -O /dev/null http://127.0.0.1:50080/healthz

Una vez verificado, añadí el healthcheck al servicio:

    healthcheck:
      test: ["CMD", "wget", "-q", "-O", "/dev/null", "http://127.0.0.1:50080/healthz"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 10s

Con esto ya teníamos otro servicio preparado para que Podman pueda verificar periódicamente su estado.

◇ FlexGet

Por último, quedaba FlexGet. Mi servicio para descargar archivos de los podcasts que más me gustan y que me gusta conservar para poder revisarlos con más calma.

Este servicio es algo diferente de los anteriores. No lo utilizo como un servidor web convencional, sino que funciona como un daemon que se encarga de ejecutar las tareas programadas para gestionar mis feeds y descargas.

Por eso, en lugar de comprobar una dirección HTTP, preferí utilizar el propio comando de FlexGet para consultar el estado del daemon.

La imagen dispone de wget, curl y python3, pero lo más interesante es que también podemos ejecutar directamente FlexGet.

Primero comprobé la versión instalada:

user@ares ~> podman exec flexget flexget --version

Y después consulté el estado del daemon:

user@ares ~> podman exec flexget flexget daemon status

La respuesta fue:

There is a FlexGet process already running for this config, sending execution
there.
Daemon running. (PID: 169)

Además, el comando devolvió un código de salida 0.

Así que utilicé esa misma comprobación para el healthcheck:

    healthcheck:
      test: ["CMD", "/usr/bin/flexget", "-c", "/config/config.yml", "daemon", "status"]
      interval: 60s
      timeout: 15s
      retries: 3
      start_period: 60s

De esta manera, no nos limitamos a comprobar que el contenedor está en ejecución, sino que preguntamos al propio FlexGet si su daemon está funcionando.

◇ Comprobando los resultados

Una vez añadidos los healthchecks y recreados los contenedores, podemos consultar su estado directamente desde Podman.

Por ejemplo:

user@ares ~> podman inspect nginxPodcast --format '{{.State.Health.Status}}'

Si todo funciona correctamente, obtendremos:

healthy

Los estados que podemos encontrar son:

  • starting: el contenedor todavía está dentro del periodo inicial de comprobación.
  • healthy: las comprobaciones se están realizando correctamente.
  • unhealthy: se han producido suficientes comprobaciones fallidas.

◇ Conclusión

Con esto ya tengo cinco servicios de mi VPS con sus respectivos healthchecks:

Servicio Comprobación
Memos Petición HTTP al puerto 5230
Element Petición HTTP al puerto 80
Continuwuity Consulta a la API de Matrix
Nginx Ruta específica /healthz
FlexGet Estado del daemon

Cada servicio necesita una comprobación diferente, dependiendo de cómo funciona y de las herramientas que incluye su imagen.

Lo que más me ha gustado de este proceso es que he podido añadir estas comprobaciones sin tener que modificar las imágenes originales de los contenedores. Aparte de lo que voy aprendiendo poco a poco sobre Podman, el funcionamiento de los contenedores y todo lo que les rodea, siempre está bien descubrir nuevas formas de mejorar nuestro setup.

Incluso en el caso de Continuwuity, que no incluye ni una shell, hemos encontrado una solución utilizando BusyBox.

Ahora que los contenedores pueden informar de su estado de salud, ya tengo preparada la base para el siguiente paso: configurar Beszel para que supervise estos estados y me avise cuando alguno de los servicios tenga problemas.

Pero eso será en otro artículo.
