Immich - Migración de V2 a V3 en producción

2026-09-07 · 9 min · @self-hosting · #docker #unRAID

Tal como había explicado en este artículo, explicaba el proceso de migración desde la versión v2 a la versión v3 de Immich en un entorno de pruebas. Ahora toca hacer lo mismo, pero en el contenedor de producción.

Como recordaréis, el despliegue de Immich mediante Docker Compose estaba formado por:

  • immich-server
  • immich-machine-learning
  • redis

Asimismo, la base de datos de PostgreSQL estaba gestionada como un contenedor independiente.

◇ Migración de producción

Una vez validado todo el proceso en el entorno paralelo immichTest, la migración de producción consistia básicamente en repetir el mismo procedimiento que habiamos utilizado anteriormente.

El objetivo es realizar el cambio con el menor tiempo de parada posible y manteniendo siempre una posibilidad de recuperación. Sé que estamos hablando de una instalación que esta ubicada en mi servidor local y es para mi uso personal, pero nunca está de más hacer las cosas rápido y bien.

Además, en este caso partimos con una ventaja importante: ya hemos realizado la migración en un entorno de pruebas. Esto me ha permitido detectar y solucionar los problemas que pueden aparecer antes de tocar la instalación de producción.

La arquitectura que tenemos actualmente es la siguiente:

Immich v2.7.5
      |
      +-- PostgreSQL externo
      |
      +-- pgvecto.rs

Después de la migración, quiero que quede de la siguiente manera:

Immich v3
      |
      +-- PostgreSQL dentro del Compose
      |
      +-- VectorChord
      |
      +-- Redis

Antes de empezar, hay una cosa que tenemos que tener muy clara: las copias de seguridad.

Al igual que hicimos durante las pruebas, vamos a realizar una copia tanto de la base de datos como de la biblioteca multimedia. De esta forma, si algo sale mal durante la migración, siempre tendremos la posibilidad de volver al estado anterior.

◇ Copias de seguridad

◈ PostgreSQL

Creamos una nueva copia de la base de datos mediante pgAdmin con el nombre:

backup_immich_pre_migracion.sql

Esta copia nos permitirá restaurar la base de datos si aparece cualquier problema durante la migración.

◈ Biblioteca multimedia

También vamos a realizar una copia de nuestra biblioteca de fotos.

Nos situamos en el directorio donde tenemos almacenadas todas nuestras fotografías:

apps@unraid ~> cd /ruta/de/biblioteca/photos

Y realizamos la copia de seguridad (yo lo hago mediante tar):

apps@unraid ~> tar -cvf /ruta/del/backup/photos_pre_migracion.tar -C /ruta/de/biblioteca/photos .

De esta forma tenemos dos puntos de recuperación: la base de datos y la biblioteca multimedia.

◇ Detener los servicios afectados en producción

Antes de realizar cualquier cambio, vamos a detener todos los servicios de Immich.

Esto es importante porque no queremos que ningún contenedor pueda realizar escrituras en nuestra biblioteca o en la base de datos mientras estamos modificando la instalación. De lo contrario, podríamos terminar con datos corruptos, lo que podría provocar problemas posteriormente.

Para ello hacemos:

apps@unraid ~> docker compose stop immich-server immich-machine-learning redis

Con esto detenemos los servicios que utilizan Immich y evitamos que se produzcan nuevas operaciones mientras hacemos el cambio.

◇ Sustitución de PostgreSQL

En la instalación original utilizaba, tal como expliqué en el artículo de pruebas de la migración:

tensorchord/pgvecto-rs:pg16-v0.3.0

La nueva imagen que vamos a utilizar será:

ghcr.io/immich-app/postgres:16-vectorchord0.3.0-pgvectors0.3.0

Eso sí, vamos a mantener el volumen existente:

/ruta/de/la/bbdd/postgres

De esta forma, la nueva imagen seguirá utilizando la misma base de datos que teníamos hasta ahora.

Nota:

No realizamos ninguna migración mediante exportación/importación del SQL porque, en este proceso, mantenemos la misma base de datos y realizamos el cambio de extensión vectorial siguiendo el procedimiento utilizado por el equipo de Immich.

◇ Primer inicio después del cambio

Una vez sustituida la imagen de PostgreSQL, procedemos a iniciar Immich manteniendo todavía la versión IMMICH_VERSION=v2.7.5.

Este paso es importante porque todavía no queremos actualizar Immich a la versión 3.

Primero queremos comprobar que la base de datos funciona correctamente con el cambio de las nuevas extensión:

PGvecto.rs --> VectorChord

Por tanto, en este punto el objetivo es comprobar que la instalación sigue funcionando como antes, pero utilizando VectorChord en lugar de PGvecto.rs.

Os recomiendo realizar las siguientes comprobaciones:

  • Acceso web.
  • Login.
  • Biblioteca.
  • Usuarios.
  • Búsquedas.
  • Machine Learning.

En mi caso, todas estas pruebas funcionaron perfectamente.

Y aquí llegó la primera alegría del proceso: la base de datos estaba funcionando correctamente con el nuevo sistema y Immich seguía operativo.

Con esto ya podemos continuar con el siguiente paso, que es la actualización de Immich a la versión 3.

◇ Actualización final a Immich v3

Ahora sí que llega el paso más importante de todo el proceso: actualizar Immich a la versión 3.

Tal como habíamos hecho durante las pruebas, solamente tenemos que cambiar:

IMMICH_VERSION=v2.7.5

por:

IMMICH_VERSION=v3

Una vez realizado el cambio, descargamos las nuevas imágenes:

docker compose pull

Y recreamos los servicios:

apps@unraid ~> docker compose up -d immich-server immich-machine-learning redis

Durante este proceso, Immich realizará automáticamente las migraciones necesarias de la base de datos.

A partir de aquí ya tenemos nuestra instalación funcionando con Immich v3, PostgreSQL con VectorChord y Redis dentro del mismo entorno de Docker Compose.

◇ Redis

Hay una parte de la migración que finalmente no realicé y que queda pendiente para el futuro: sustituir Redis por Valkey.

Actualmente seguimos utilizando:

redis:
  image: docker.io/redis:6.2-alpine

La documentación de Immich recomienda realizar esta migración, pero en mi caso preferí no mezclar más cambios dentro de la migración a Immich v3.

Creo que es mejor hacer este tipo de cambios por separado. De esta forma, si aparece algún problema, resulta mucho más sencillo saber de dónde viene.

Cuando llegue el momento de realizar el cambio de Redis a Valkey, volveré a realizar las pruebas en el entorno paralelo antes de aplicarlo en producción.

Una cosa cada vez. 😅

◇ Procedimiento de rollback

Con esto ya hemos terminado la migración, pero siempre puede aparecer algún problema que no habíamos previsto.

Quien esté libre de culpa, que tire la primera piedra.

Precisamente por eso hemos realizado las copias de seguridad antes de empezar. Si algo sale mal, tenemos que poder volver al estado anterior.

En mi caso no fue necesario realizar el rollback, pero el procedimiento sería el siguiente.

◈ Detener la instalación nueva

Primero detenemos los servicios de Immich:

apps@unraid ~> docker compose stop immich-server immich-machine-learning redis

◈ Restaurar PostgreSQL original

Volvemos a utilizar la imagen original de PostgreSQL:

tensorchord/pgvecto-rs:pg16-v0.3.0

manteniendo el volumen original:

apps@unraid ~> /ruta/de/la/bbdd/postgres

De esta forma volvemos a utilizar la instalación de PostgreSQL que teníamos antes de comenzar la migración.

◈ Restaurar la biblioteca multimedia

Para recuperar la biblioteca original, restauramos la copia que hemos realizado anteriormente:

apps@unraid ~> tar -xvf photos_pre_migracion.tar -C /ruta/de/biblioteca/

◈ Volver a la versión anterior de Immich

Por último, volvemos a modificar la versión de Immich:

IMMICH_VERSION=v2.7.5

Y recreamos los contenedores:

apps@unraid ~> docker compose up -d immich-server immich-machine-learning redis

Con esto deberíamos volver a tener la instalación en el estado anterior a la migración.

◇ Comprobaciones posteriores a la migración

En mi caso, como no tuve ningún problema durante la migración, volví a realizar las mismas pruebas que había hecho después del cambio de la BBDD.

La idea es comprobar que no solamente podemos acceder a Immich, sino que todos los elementos importantes siguen funcionando correctamente.

◈ Aplicación Immich

  • Login correcto.
  • Usuarios existentes.
  • Fotografías disponibles.
  • Vídeos reproducibles.
  • Álbumes intactos.
  • Comparticiones existentes.

◈ PostgreSQL

También verificamos que tenemos correctamente instaladas las extensiones necesarias mediante una consulta SQL:

SELECT extname, extversion FROM pg_extension ORDER BY extname;

Donde tendremos que encontrar:

vector
vchord

También verificamos que tenemos la versión correcta de PostgreSQL:

SELECT version();

En este caso deberíamos obtener una versión PostgreSQL 16.x.

◈ Docker

Por último, y no menos importante, comprobamos que todos los contenedores relacionados con Immich están funcionando correctamente:

docker ps

Donde deberíamos visualizar:

immichServer
immichMachineLearning
immichRedis
immichPostgres

Aunque pueda parecer una comprobación de puro trámite, nunca está de más echarle un vistazo.

◇ Problemas conocidos y observaciones

En mi caso, aunque todo estaba funcionando perfectamente, al revisar los logs de Immich encontré un par de mensajes que me llamaron la atención.

No me impedían utilizar Immich, pero creo que merece la pena dejarlos documentados por si en el futuro vuelven a aparecer o alguien se encuentra con el mismo problema.

◈ Mensajes de VectorChord durante el arranque

Durante el inicio de PostgreSQL observé este mensaje:

WARNING: Failed to maintain vector indexes:
Failed to create RPC client.

Lo curioso es que, a pesar de este mensaje, todo estaba funcionando correctamente.

La BBDD se iniciaba sin problemas y las extensiones estaban disponibles:

  • vector
  • vchord

Por ese motivo, en mi caso, lo dejé como un mensaje pendiente de investigar.

Si alguien sabe exactamente por qué aparece este mensaje y qué significa, ya me lo dirá. 😅

◈ Error de usuario root

También apareció el siguiente mensaje:

FATAL: role "root" does not exist

Por lo que pude comprobar, algún proceso está intentando conectarse a PostgreSQL utilizando root como usuario.

Lo curioso es que root es un usuario del sistema Linux y no un usuario de la base de datos.

En cualquier caso, este mensaje tampoco me impedia utilizar correctamente Immich, así que lo dejo igualmente documentado como otra cosa pendiente de investigar.

◇ Conclusiones

Pues llegamos al final de este artículo.

Si hay algo que me ha quedado claro después de todo este proceso es que realizar primero la migración en un entorno paralelo ha sido todo un acierto.

Gracias a las pruebas con immichTest, pude detectar los problemas que podían aparecer, solucionarlos y, sobre todo, llegar a la migración de producción sabiendo exactamente qué pasos tenía que realizar.

Eso no significa que una migración vaya a salir siempre perfecta. Pueden aparecer problemas nuevos que no hayamos contemplado, pero al menos hemos reducido bastante los riesgos y tenemos un procedimiento de recuperación preparado.

Gracias a esta migración paralela pude verificar:

  • La actualización de PostgreSQL mediante el cambio de PGvecto.rs a VectorChord.
  • La integración completa de PostgreSQL en el entorno de Docker Compose de Immich.
  • La administración de PostgreSQL mediante pgAdmin a través de la red interna de Docker utilizada por Immich.
  • La preservación y compatibilidad con los datos existentes.
  • El mantenimiento de los nombres de servicio Docker necesarios para garantizar el correcto funcionamiento de Immich.

Con todo esto, la arquitectura final queda de la siguiente manera:

Unraid
├── Docker Compose
├──── Immich Server
├──── Immich Machine Learning
├──── Redis
└──── PostgreSQL + VectorChord
          |
          |
       pgAdmin

El proceso de migración se ha realizado de forma controlada y por fases:

  • Migración de PostgreSQL.
  • Validación con Immich v2.7.5.
  • Actualización a Immich v3.
  • Comprobaciones posteriores.
  • Cambios opcionales posteriores, como la futura migración de Redis a Valkey.

Al hacerlo de esta manera, he reducido los riesgos y, además, he mantenido un punto de restauración que me permitiría volver al estado anterior si algo hubiera salido mal.

Y con esto sí que damos por finalizados los dos artículos en los que explico mi proceso de migración a Immich v3, tanto en la fase de pruebas como en producción.

Actualmente lo tengo funcionando en producción sin ningún problema.

Y, como siempre, si algo he aprendido de todo esto es que hacer las pruebas antes de tocar producción sigue siendo una muy buena idea. 😅
